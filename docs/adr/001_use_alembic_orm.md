# ADR 001: Use Alembic with raw SQL migrations instead of an ORM

**Status:** Accepted
**Date:** 2026-08-07

## Context

The database schema for this project is expected to change repeatedly as the
pipeline evolves — new metrics will surface once the synthetic data generator
and the Garmin ingestion are running, multi-user support introduces
authentication fields, and the analytical model may need reshaping as query
patterns become clearer.

Applying schema changes by hand is not viable: there would be no history of how
the schema evolved, no way to recreate the database from scratch reliably, and
no way to revert a change. Schema migrations therefore need to be versioned
alongside the application code.

In the Python ecosystem, the conventional answer is Alembic, and Alembic is
most commonly paired with the SQLAlchemy ORM — which enables autogenerated
migrations by comparing Python model classes against the live database. This
combination is close to a default in modern FastAPI projects.

## Decision

Use Alembic for schema versioning, but write migrations as raw SQL via
`op.execute(...)` rather than adopting the SQLAlchemy ORM at this stage.

## Rationale

The primary benefit being sought is *versioned, reversible, reproducible schema
changes*. Alembic delivers that on its own; the ORM is a separate concern that
happens to be commonly bundled with it.

Given existing familiarity with PostgreSQL — including functions, triggers and
query optimisation — writing the DDL directly is faster and clearer than
expressing it through an abstraction layer, and it keeps full control over
constructs that ORMs tend to handle awkwardly (partial indexes, triggers,
custom functions).

Adopting the ORM now would add a second learning curve on top of Alembic itself,
at a point in the project where the priority is getting data flowing end to end.

### Alternatives considered

- **Alembic + SQLAlchemy ORM** — the ecosystem default, and it enables
  `--autogenerate`. Rejected for now to avoid introducing two new abstractions
  simultaneously, and because the SQL-level control matters more at this stage
  than the convenience of autogeneration.
- **Plain SQL scripts in the Postgres init directory** — trivial to set up, but
  they only run on first volume initialisation. Applying a change later would
  require destroying and recreating the database, and there would be no history
  or rollback path.

## Consequences

### Positive

- Full control over the generated DDL, including PostgreSQL-specific features.
- Smaller conceptual surface: one new tool (Alembic) rather than two.
- Migrations read as SQL, which is directly reviewable and portable.

### Negative

- No `--autogenerate`: every migration is written by hand, which is slower and
  leaves more room for human error.
- The current schema is not represented anywhere in Python, so application code
  has no typed model of the tables it queries.
- Diverges from the most common FastAPI project layout, which may be mildly
  surprising to other developers.

### Revisit when

This decision should be reconsidered if hand-written migrations start to feel
error-prone, or if typed models would meaningfully improve the API layer.

Migrating to SQLAlchemy later is expected to be straightforward: existing
migrations remain valid regardless of how they were authored, and the ORM can be
introduced by declaring model classes that describe the schema already in place
— a correct set of classes should produce an empty autogenerated migration,
which doubles as verification that the two representations agree.

The larger part of that migration would be the query layer rather than the
schema. Keeping all SQL confined to `api/repositories/` is therefore a
deliberate constraint of this decision, so that any future transition stays
contained to a single module.
